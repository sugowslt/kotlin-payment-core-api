# 금액·수수료·정산 금액 계산 정책

## Context

현재 결제 금액은 `BigDecimal`로 저장하지만 수수료율, 수수료 금액, 가맹점 정산 금액의 계산 규칙은 정의되어 있지 않았습니다. 이 규칙이 API·배치·재처리 코드에 흩어지면 반올림 차이와 재실행 결과 불일치가 발생할 수 있습니다.

## Decision

- 수수료율은 basis point(`feeRateBps`)로 표현합니다. `100 bps = 1%`입니다.
- 결제 금액은 소수 둘째 자리까지 허용합니다.
- 수수료 금액은 `grossAmount × feeRateBps ÷ 10,000`을 계산한 뒤 소수 둘째 자리에서 `HALF_UP`으로 반올림합니다.
- 정산 금액은 `grossAmount - feeAmount`로 계산합니다.
- 수수료율은 `0`부터 `10,000`까지 허용합니다.
- 입력 금액과 수수료율만으로 결과가 결정되도록 순수 calculator로 구현합니다. 같은 입력을 재처리하면 같은 결과가 나옵니다.
- 이번 단계에서는 기존 결제 생성·승인 API 응답과 DB schema를 변경하지 않습니다. 실제 정산 원장과 지급 상태는 별도 도메인으로 확장합니다.

## Alternatives

1. 퍼센트 문자열 또는 `Double` 사용
   - 부동소수점 오차와 표현 형식 차이가 발생할 수 있어 선택하지 않았습니다.
2. 원 단위 절사
   - 수수료가 과도하게 줄어들고 정책 변경 시 결과 차이가 커질 수 있어 `HALF_UP`을 선택했습니다.
3. 결제 service 내부에서 직접 계산
   - 승인·취소·정산 재처리 경로마다 규칙이 복제될 수 있어 독립 calculator로 분리했습니다.

## Consequences

- 계산 결과를 단위 테스트로 고정하고 재처리 시 결과를 재현할 수 있습니다.
- 실제 가맹점별 수수료율, 세금, 최소 수수료, 정산 주기는 후속 정책으로 분리해야 합니다.
- 계산 결과를 DB에 저장할 때는 원금·수수료율·수수료·정산 금액을 함께 보존해야 사후 검증이 가능합니다.
