# 로컬 부하 테스트와 Docker Compose 경계

## 상태

수용. 실제 부하 수치는 기본 H2 로컬 조건으로 기록했고, 컨테이너 연결 검증까지 완료했다.

## 결정

- 부하 테스트는 Node 내장 `fetch`만 사용해 외부 SaaS와 추가 유료 도구 의존성을 만들지 않는다.
- 기본 대상은 읽기 전용 cursor 조회 API로 두고, 요청 수·동시성·기대 상태 코드를 환경변수로 바꿀 수 있게 한다.
- 결과에는 평균·p50·p95·min·max·상태 코드별 건수·실패율을 함께 출력한다.
- 기대 상태 코드와 다른 응답이 하나라도 있으면 프로세스 종료 코드를 1로 설정한다.
- MySQL과 Redis는 `compose.yaml`에서 healthcheck와 named volume을 갖는 로컬 의존성으로만 제공한다.
- 애플리케이션 이미지는 이번 단계에서 만들지 않고, 로컬 Spring Boot 프로세스가 Compose의 MySQL·Redis에 연결하는 구성을 기준으로 한다.

## 이유

- 부하 측정 결과를 특정 도구의 리포트 형식보다 단순한 stdout으로 남기면 실행 조건과 함께 문서화하기 쉽다.
- 조회 API는 결제 상태를 변경하지 않아 반복 측정의 외부 부작용이 작다.
- Compose에 애플리케이션까지 포함하면 이미지 빌드·환경변수·운영 배포 범위가 커지므로 이번 단계에서는 의존성 컨테이너만 고정한다.

## 제약

- 실제 p95·처리량은 서버 실행 상태, 데이터 건수, DB, JVM, 동시성에 따라 달라진다.
- Docker 실행과 실제 API 부하 측정 없이는 성능 개선이나 처리량을 주장하지 않는다.

## 기록된 측정값

2026-07-26 기본 H2 환경에서 readiness 확인 후 별도 워밍업 없이 cursor 조회 API를 100건·동시성 10으로 호출했다. 100건 모두 HTTP 200이었고 실패율은 0%였다. 평균 71.04ms, p50 14.26ms, p95 562.78ms, min 7.17ms, max 658.41ms였다. 단일 로컬 실행이므로 운영 성능이나 처리량으로 일반화하지 않는다.

측정 준비 중 PowerShell `Start-Process`가 stdout과 stderr에 같은 redirect 파일을 받아들이지 않는 오류가 발생했다. 두 로그 파일을 분리해 재실행했고, 측정 후 8080 포트를 확인해 정리했다.

## Compose 검증 결과

기존 `payment-core-mysql` 컨테이너가 호스트 3307을 사용해 Compose MySQL bind가 실패했다. 기존 컨테이너를 중지하지 않고 Compose MySQL을 3308로 노출하도록 변경했다. 이후 Compose 문법과 healthcheck가 통과했고, MySQL Flyway V1·V2·V3와 Redis `SET NX EX` 동작을 확인했다. Compose MySQL·Redis 환경의 전체 테스트는 67개 성공, 실패 0개, 오류 0개, skipped 0개였다.
