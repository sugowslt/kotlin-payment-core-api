# ADR: FAILED 아웃박스 수동 복구

- 상태: Accepted
- 날짜: 2026-07-24
- 범위: 최종 실패 아웃박스 이벤트의 운영자 재처리

## 배경

아웃박스 이벤트가 최대 재시도 횟수를 넘으면 자동 처리 대상에서 빠지고 `FAILED`가 됩니다. 일시적인 외부 publisher 장애가 복구된 뒤 운영자가 해당 이벤트를 다시 처리할 수 있는 명시적인 복구 경로가 필요합니다.

## 결정

- `POST /api/v1/internal/outbox/{eventId}/retry`를 추가합니다.
- endpoint는 기존 `X-Webhook-Replay-Token`으로 보호합니다.
- 대상 이벤트가 없으면 `404 OUTBOX_EVENT_NOT_FOUND`를 반환합니다.
- 대상 상태가 `FAILED`가 아니면 `409 INVALID_OUTBOX_STATUS`를 반환합니다.
- 수동 복구 시 상태를 `PENDING`으로 되돌리고 retry budget을 0부터 다시 시작합니다.
- 다음 시도 시각은 즉시로 설정하고, 이후 발행 worker 또는 로컬 publish endpoint가 동일한 흐름으로 처리합니다.

## 대안과 선택 이유

1. 운영자가 DB를 직접 수정하는 방법
   - 빠르지만 감사 가능한 API 경계와 상태 검증이 없어 실수 가능성이 큽니다.
2. `FAILED` 이벤트를 자동으로 무한 재시도하는 방법
   - 원인 해결 전 반복 실패를 만들고 운영자가 장애 규모를 파악하기 어렵습니다.
3. 인증된 수동 복구 endpoint를 제공하는 방법
   - 복구 대상을 명시하고 상태·권한을 검증하면서도 외부 브로커 없이 운영 시나리오를 재현할 수 있어 선택했습니다.

## 제한과 다음 단계

- 현재 인증은 로컬 운영용 replay token이며, 운영 환경에서는 별도 운영자 인증·감사 로그 정책이 필요합니다.
- 실제 broker를 연결할 때 수동 복구 요청과 publisher 결과를 추적할 운영 이벤트를 추가 검토합니다.
