# 승인 동시성 제어 방식 결정

## 배경

승인 API는 결제 상태가 `PENDING`일 때만 `APPROVED`로 전이해야 합니다. 승인 멱등키를 저장해 같은 키의 재요청을 재사용하도록 했지만, 동시에 서로 다른 요청이 들어오면 두 트랜잭션이 같은 `PENDING` 상태를 읽을 수 있습니다.

이 경우 애플리케이션 코드의 상태 확인만으로는 마지막 저장 요청이 승인 멱등키를 덮어쓸 수 있어, 결제 승인 처리의 직렬성이 보장되지 않습니다.

## 선택지

1. 애플리케이션 락만 사용
   - 구현은 간단하지만 서버가 여러 대로 늘어나면 프로세스 간 제어가 되지 않습니다.
2. 승인 전용 원자적 UPDATE 사용
   - 경합에는 강하지만, 같은 키 재요청 시 기존 승인 응답을 반환하려면 별도 조회와 결과 분기가 필요합니다.
3. 승인 대상 행에 비관적 쓰기 잠금 적용
   - 트랜잭션 안에서 결제 행을 잠그고 상태·멱등키를 함께 확인할 수 있습니다.

## 결정

승인 경로에서만 `findByIdAndDeletedFalseForUpdate`를 사용하고 `PESSIMISTIC_WRITE`를 적용했습니다. 조회·취소 경로에는 기존 조회 메서드를 유지해 불필요한 잠금 범위를 넓히지 않았습니다.

## 이유

- 승인 상태와 승인 멱등키를 같은 결제 행에서 원자적으로 판단할 수 있습니다.
- 기존의 같은 키 재요청 응답과 다른 키 충돌 응답 규칙을 유지할 수 있습니다.
- 결제 승인이라는 짧은 임계 구간에만 잠금을 적용해 영향 범위를 제한할 수 있습니다.

## 검증

- 승인 서비스 단위 테스트에서 승인 경로가 잠금 조회 메서드를 호출하는지 검증했습니다.
- 전체 Gradle 테스트를 실행했고 27개 테스트가 모두 성공했습니다.

## 남은 한계

현재 테스트는 H2 기반 통합 테스트와 단위 테스트 중심입니다. 운영 MySQL의 잠금 대기시간, 타임아웃, 재시도 정책은 실제 DB 설정과 부하 조건에서 별도로 점검해야 합니다.
