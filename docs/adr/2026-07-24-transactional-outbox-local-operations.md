# ADR: 트랜잭션 아웃박스와 로컬 운영 대시보드

- 상태: Accepted
- 날짜: 2026-07-24
- 범위: 결제 상태 변경 이벤트의 로컬 저장과 운영 확인

## 배경

결제 생성·승인·취소와 웹훅 상태 보정이 성공했을 때, 이후 이벤트 발행이 실패하면 결제 상태와 외부 소비자 상태가 달라질 수 있습니다. 이 프로젝트는 현재 외부 Kafka나 클라우드 메시징을 사용하지 않으므로, 먼저 결제 변경과 이벤트 저장을 같은 데이터베이스 트랜잭션 안에서 확인할 수 있는 최소 경계를 마련합니다.

## 결정

- `payment_outbox_events` 테이블에 결제 변경 이벤트를 `PENDING`으로 저장합니다.
- 이벤트 payload에는 운영 확인에 필요한 payment ID, order ID, 상태, provider transaction ID만 저장하고 결제 수단 원문이나 인증정보는 저장하지 않습니다.
- 로컬 운영 endpoint의 `publish`는 외부 브로커 발행이 아니라 대기 이벤트를 `PUBLISHED`로 바꾸는 시뮬레이션입니다.
- Vue 대시보드의 `운영 대시보드` 탭에서 웹훅 지표와 아웃박스 상태를 조회하고, 대기 이벤트의 로컬 처리를 실행할 수 있습니다.
- 내부 endpoint는 `X-Webhook-Replay-Token`으로 보호합니다. 로컬 기본 토큰은 데모 편의를 위한 값이며 운영 환경에서는 `PAYMENT_WEBHOOK_REPLAY_TOKEN`으로 교체해야 합니다.

## 대안과 선택 이유

1. 바로 Kafka를 붙이는 방법
   - 실제 운영 구조와 가깝지만 브로커 운영, 인증, 재시도 정책까지 범위가 커지고 현재 목표인 결제 일관성 검증을 흐릴 수 있습니다.
2. 메모리 큐만 사용하는 방법
   - 구현은 간단하지만 애플리케이션 재시작 시 이벤트가 사라져 트랜잭션 아웃박스의 핵심 검증을 할 수 없습니다.
3. DB 아웃박스를 먼저 적용하는 방법
   - 현재 사용하는 H2/MySQL에서 재현 가능하고, 결제 변경과 이벤트 저장의 원자성 및 운영 상태를 비용 없이 확인할 수 있어 선택했습니다.

## 제한과 다음 단계

- 현재 `publish`는 실제 외부 브로커 발행이나 consumer offset 관리를 구현하지 않았습니다. worker 활성화와 DB 잠금 기준은 [아웃박스 worker ADR](2026-07-24-outbox-worker-concurrency.md), 재시도·최종 실패 상태 기준은 [아웃박스 재시도 ADR](2026-07-24-outbox-retry-policy.md)에서 관리합니다.
- 다음 단계에서 브로커를 도입하더라도 이 테이블을 발행 기준으로 유지하고, publisher 오류 분류와 최종 실패 알림을 별도 정책으로 검토합니다.
- Toss 실결제 API와 외부 유료 모니터링 서비스는 이 결정과 검증에서 사용하지 않았습니다.
